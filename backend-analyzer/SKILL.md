# 后端项目深度解析

把一个对读者完全陌生的后端项目，变成一套"陌生人 30 分钟看懂全貌、想深入时逐模块可查"的中文解析文档集（落在 `docs/analysis/`），外加一个双击即开的交互式 HTML 报告。

**本技能目录** = 本 SKILL.md 所在目录；下文以 `<skill>` 指代。写文档前必读两个参考文件：

1. `<skill>/references/spring-boot-playbook.md` —— 侦查与追链方法（阶段 1 开始前读）
2. `<skill>/references/doc-templates.md` —— 输出文档的骨架（写第一个文档前读）

画图遵守 `<skill>/references/mermaid-rules.md`。

## 铁律（任何时候不得违反）

1. **只读分析**：不修改业务代码；只允许在输出目录（默认 `docs/analysis/`）下创建文件。
2. **有理有据**：每个论断附 `相对路径:行号` 证据；查不到代码依据的判断必须写 `> ⚠️ 推测：` 并说明推测依据，宁可少说不可编造。
3. **全部中文**输出。
4. **模块 = 业务域**（auth、student、course），不是 controller/service 技术分层包。
5. **单张 Mermaid 图 ≤ 15 个节点**，超了拆图并编号衔接。
6. **优化建议五段式**：现状证据 → 问题 → 影响 → 建议方案 → 预期收益，缺一不可，禁止"建议加强XX"式空话。
7. **入口点零遗漏**：所有 controller 方法、定时任务、消息消费者都必须出现在某个模块的功能清单里。

## 第 0 步：确认输入并选模式

**确认目标项目**：确定目标项目根（工作区本身，或用户指定的子目录/路径）。若用户没指明且工作区里有多个像后端项目的目录（各有 pom.xml/build.gradle），列出候选让用户选，不要擅自挑一个。分析产物落在**目标项目根**下的 `docs/analysis/`（如分析 `fixtures/demo-campus`，产物就在 `fixtures/demo-campus/docs/analysis/`）——文档跟着项目走。仅当目标项目在工作区之外（绝对路径）时，先提示用户"建议用 ZCode 打开目标项目再分析"；用户坚持就地分析时按单会话模式 + 绝对路径进行。

**过程可见**：开工时用 TodoWrite 把流水线建成任务清单（侦察 / 全局架构 / 逐模块深挖 / 优化评审 / 独立复核 / 汇编导读），每完成一个阶段就更新状态——用户随时能看到分析进行到哪一步。每个阶段完成后再用一两句话向用户汇报关键发现。

**探测规模**（在目标项目根目录执行）：

```bash
find . -path ./node_modules -prune -o -name "*.java" -not -path "*/target/*" -print | wc -l
```

再按 playbook §3.1 判断业务模块数。

**选模式**：

| 情况 | 模式 |
|---|---|
| 用户说"快速/大概过一下" | 单会话 |
| 用户说"深入/workflow/并行/多智能体" | workflow 模式 |
| 自动：Java 文件 > 40 或业务模块 > 4 | workflow 模式 |
| 自动：其余 | 单会话 |

向用户一句话说明选了哪种模式及原因，然后开工。

## 单会话流水线（小项目，主 agent 自己执行）

五个阶段顺序执行，每个阶段完成后用一两句话向用户汇报关键发现。

### 阶段 1 · 侦察
按 playbook §1-§2：读 pom/build、application.yml、启动类；grep 枚举全部入口点，登记成"接口清单表"（HTTP 方法 + 完整路径 + 类.方法）。产出：技术栈清单 + 入口点清单。

### 阶段 2 · 全局架构
按 playbook §3 划分模块（给证据），梳理模块间联系的三类证据（§4.3）。产出：分层图、模块关系图、表清单。此时把模块列表定下来——**后续所有文档的模块划分必须与这里一致**。

划分定稿后，向用户展示一份模块清单预览（模块名 + 职责一句话 + 入口点数量），并说明"如需增删或改名随时打断，我按此继续"——不用等用户回复，展示后直接进入阶段 3；workflow 模式下同样在侦察结果出来后向用户转述模块划分。

### 阶段 3 · 逐模块深挖
对每个业务模块，按 doc-templates §3 的模块模板写 `docs/analysis/modules/<模块名>.md`。每份模块文档必须三层齐全，让模块"分得开、连得上"：
- **模块位置图**（§1 开头）：以本模块为中心的小关系图，一眼看清它和谁有关系；
- **功能清单**（§2）：覆盖全部入口点，"流程"列用 `[图 N-M](#图 N-M)` 页内锚点直达流程图；
- **功能详解**（§3）：逐功能"设计意图 → 流程图 → 步骤表 → 流程跳转 → 设计评价"，追链追到 SQL 与表（§4.1-§4.2），横切关注点画进流程；
- **功能跳转地图**（§4）：本模块功能间的操作路径图（跨模块跳转用虚线标注），配 2-3 句最典型路径的文字说明；
- 编号规则：小节编号全项目统一（1-6），图编号带模块序号（图 4-1），图标题注释必须是 mermaid 块内第一行。

支撑设施（common 等）写入总架构文档，不单独成模块文档。

### 阶段 4 · 优化评审
对每个模块过 playbook §6 的检查清单，把命中项按五段式写进该模块文档的"优化建议"小节，编号 O1、O2……全项目唯一。每条建议必须指着代码说话；确认不了的不写或标推测。

### 阶段 4.5 · 独立复核（准确性关卡，不得跳过）
所有文档写完后，按以下优先级复核（自己写的东西自己看不出错）：

**首选：派独立子代理。** 用 Agent 工具派一个**全新的**子代理（看不到你的分析过程）复核：
1. 每份模块文档抽查 3-5 处「文件:行号」证据，打开源文件核实是否真实支撑所述内容；
2. 核对每份模块文档的功能清单与阶段 1 的入口点清单是否一一对上；
3. 每张流程图抽 2-3 个关键节点，核对分支条件/失败出口与代码中的 if/异常处理一致。

**回退：机械化复核**（没有子代理工具可用时，如你本身就是子代理）。写一个临时校验脚本或逐条 grep：把全部文档中出现的「文件路径:行号」引用提取出来，逐条校验该文件存在且行号在文件行数范围内；再对其中最关键的 15-20 处（高危问题的证据、流程图分支标注）人工打开源文件做语义核对。发现偏差立即修正对应文档。

复核完成后：向用户简报结果（"独立复核抽查 N 处证据，发现并修复 M 处偏差"），并重跑构建确认退出码 0。

### 阶段 5 · 汇编与生成 HTML
1. 写 `<目标项目根>/docs/analysis/00-architecture.md`（含优化建议汇总表，用锚点链接到各模块详情）；
2. 写 `<目标项目根>/docs/analysis/README.md`（导读：阅读顺序说清"为什么"、快速上手路径、术语表）；
3. 生成 HTML 报告（--src 指向目标项目下的输出目录）：

```bash
node "<skill>/scripts/build_report.mjs" --src "<目标项目根>/docs/analysis"
```

退出码 1 表示有 mermaid 语法问题（错误信息会指出哪个文件的哪个图块）：修复对应文档后重跑，直到退出码 0。

## workflow 模式（大项目，多智能体并行）

调用已保存的 workflow（`projectPath` 传目标项目根相对当前工作区的路径，`"."` 表示工作区本身）：

```
CreateWorkflow  saved: { name: "backend-analyze", args: { projectPath: "<项目根相对路径>" } }
```

若 `ListSavedWorkflows` 里没有 `backend-analyze`，改用文件提交：
`CreateWorkflow  path: "<skill>/assets/backend-analyze.dwf.ts", args: { projectPath: "<项目根相对路径>" }`，
并在运行结束后建议用户把它保存为全局工作流（一句话即可，用户同意再保存）。

**workflow 跑完后你必须亲自核对，核对通过才算完成**：

1. `docs/analysis/` 下 README.md、00-architecture.md、modules/*.md、report.html 齐全；
2. 模块文档数量与阶段侦察的模块列表一致，无遗漏；
3. 抽查 3 条 `文件:行号` 证据，确认真实存在且指向所述内容；
4. HTML 构建退出码为 0（workflow 会保证，失败会自修复重试）；
5. 发现缺漏：小问题直接自己补写修复，大问题（整模块缺失）用单会话流水线补齐。

若 workflow 运行失败或被停止：不要重头再来，降级为单会话流水线继续——已生成的文档沿用，只补缺失部分。

## 收尾自检（两种模式通用）

- [ ] 入口点清单与各模块功能清单能一一对上，无遗漏；
- [ ] 每个业务模块文档都有功能流程图；总架构有分层图、模块关系图、ER 图；
- [ ] 优化建议编号唯一、五段式齐全、汇总表与详情一致；
- [ ] README 有阅读顺序（含理由）、快速上手路径、术语表；
- [ ] `build_report.mjs` 退出码 0，report.html 已生成；
- [ ] 业务代码零改动（可用 `find <目标项目> -name "*.java" -newer <基准文件>` 或核对文件修改时间确认）。

最后向用户汇报：产出了哪些文件（给路径）、一句话总结项目架构、3-5 条最重要的发现/优化建议、提示打开 `docs/analysis/report.html` 阅读（附一句使用提示：侧边栏可跨页搜索、可看本页目录、←/→ 键翻页、点流程图放大）。汇报末尾附"接下来你可以"，例如：让某个模块的讲解更细、追问某条优化建议的具体改造步骤、或指定下一个要分析的项目。

## 常见误区

- 把 controller/service/mapper 当成模块 → 重读 playbook §3.1；
- 只看 controller 就下结论 → 追链必须追到 SQL 与表，横切关注点（拦截器/AOP/事务）必须画进流程；
- 流程图凭想象 → 每个箭头都要有代码依据，失败分支来自异常处理代码；
- 优化建议只有观点没有证据 → 五段式第一段就是"现状证据"，写不出证据的建议删掉；
- 图渲染失败不改 → build 报错信息会定位到文件与图块，修完重跑到退出码 0 为止。
